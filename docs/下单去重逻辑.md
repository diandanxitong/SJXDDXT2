# 下单去重逻辑说明（幂等键版本）

这份文档描述 `客户端/customer.html` 里 `submitOrder()` 完整的下单流程，包括本机重试
和同桌多设备两类重复下单场景的处理机制。目的是给外部技术审阅用，欢迎挑潜在漏洞。

## 系统背景（约束条件）

- 纯静态网页 + Firestore，没有自己的后端服务器，没有 Cloud Functions（刻意保持在
  Firebase 免费 Spark 方案，不引入需要付费方案的能力）
- 顾客端没有登录态——扫桌上二维码即用，Firestore 安全规则靠"数据形状对不对"兜底
- 同一桌可能有多台手机同时在点（一家人/一桌朋友各自扫码）

## 要解决的两类问题

1. **本机重试**：网络卡顿，客户端等不到确认，用户自己再点一次"确认下单"（或者
   请求在客户端已经超时判定失败，但服务器那边其实收到了）
2. **同桌多设备各自提交**：几台手机看着同一份共享购物车，几乎同时点了"确认下单"

这两个问题用不同机制解决，不能用同一套逻辑通吃——本机重试可以靠一个客户端生成的
标识符精确识别"这是同一次尝试"；跨设备提交没有这种共享标识符（两台设备各自生成
的标识天然不相关），只能靠"谁先抢到共享状态"来判定。

## 核心数据结构

**`tableCarts/{桌号}`（共享购物车草稿）**
```
{ items: { [菜品id]: { qty, spice, size, excludes, cookMethod } | null }, updatedAt: number }
```
顾客选菜过程中每次改动都实时写进这里，同桌所有设备都在监听、合并进本地状态。

**`orders/{文档id}`（正式订单）**
```
{ table, items: [...], createdAt, nickname, partySize, status: 'pending', isAddOn }
```
`文档id` 现在是客户端生成的幂等键（不再用 Firestore 自动生成的 id）。

## 幂等键：生成、存放、清除（v2：绑定内容指纹）

**第一版有一个已确认修复的漏洞**：键只绑定桌号，不绑定内容。场景是——顾客提交
`[A,B]`，服务器其实建单成功了，但客户端超时判定失败；顾客往购物车又加了 `C`
（变成 `[A,B,C]`）再点确认；因为读到的还是同一个键，事务发现这个键已经建过单，
直接判定 `alreadyExists` 复用旧订单——`C` 从此消失，界面还显示成功。这是比重复
下单更隐蔽的丢单，因为没有任何报错。

修法：存键的同时存一份内容指纹（复用已有的 `itemsSignature`，不用重新发明规范化
逻辑），取键时先比对指纹，指纹不一样就说明这不是同一份提交意图，必须发新键。

```js
const IDEMPOTENCY_KEY_PREFIX = 'pendingOrderKey:';

function genIdempotencyKey(){
  try{ if(window.crypto && crypto.randomUUID) return crypto.randomUUID(); }catch(e){}
  return 'k' + Date.now().toString(36) + Math.random().toString(36).slice(2);
}

function getOrCreateIdempotencyKey(table, items){
  const storageKey = IDEMPOTENCY_KEY_PREFIX + table;
  const fingerprint = itemsSignature(items);
  try{
    let cached = null;
    try{ cached = JSON.parse(sessionStorage.getItem(storageKey) || 'null'); }catch(e){ cached = null; }
    if(cached && cached.key && cached.fingerprint === fingerprint) return cached.key;
    const fresh = { key: genIdempotencyKey(), fingerprint };
    sessionStorage.setItem(storageKey, JSON.stringify(fresh));
    return fresh.key;
  }catch(e){
    // sessionStorage 不可用（极少数受限环境）：退化成纯内存变量，
    // 页面刷新会丢失这份保护，但不会导致代码崩溃
    const cached = memoryIdempotencyKeys[table];
    if(cached && cached.fingerprint === fingerprint) return cached.key;
    const fresh = { key: genIdempotencyKey(), fingerprint };
    memoryIdempotencyKeys[table] = fresh;
    return fresh.key;
  }
}
```

- **生成时机**：`submitOrder()` 每次被调用都会走 `getOrCreateIdempotencyKey`——如果
  `sessionStorage` 里存的指纹跟这次要提交的内容一致，复用同一个键（不管隔了多久，
  这是真正的重试）；指纹不一致（购物车内容变了），发一把新键。
- **存放位置**：`sessionStorage`，key 是 `pendingOrderKey:{桌号}`，值是
  `{ key, fingerprint }`。选 sessionStorage 是因为生命周期正好卡在"页面刷新还能
  读到"（断网重试时用户习惯性刷新页面，是最容易触发重复下单的场景之一）和"关掉
  标签页/清场换下一桌自动失效"这两个需求中间，不需要自己再实现过期时间判断。
- **清除时机**：`submitOrder()` 确认拿到 `docId`（不管是新建、命中已存在、还是命中
  同桌别人建的那笔）之后，立刻调用 `clearIdempotencyKey(table)`。如果这次提交最终
  走进了 `catch`（真正的异常/超时），**不清**——留给下一次点击复用，也留给
  `reconcilePendingSubmits` 事后核对。

## 核心机制：合并事务（v2：写入内容从事务内现读的草稿现算）

**这里也有一个已确认修复的漏洞**：原来的写法是事务只用草稿的内容做了一次布尔
判断（草稿是不是空的），真正写进订单的却是函数外部闭包住的 `order.items`——一份
在事务开始之前、在本机某个更早的时间点算好的快照。

问题在于 Firestore 事务的自动重试机制恰恰在"这份快照可能已经过期"的窗口里生效：
A、B 两台设备共享同一份草稿 `[X,Y]`；A 点击确认，事务开始读草稿的同时，B 往草稿里
加了 `Z`（变成 `[X,Y,Z]`）；Firestore 检测到 A 读过的 `draftRef` 已被修改，自动
重跑整个事务；重跑后再读草稿是 `[X,Y,Z]`，"草稿非空"这个判断照样通过——但如果
写入用的还是最初那份 `[X,Y]` 快照，`Z` 就会在 `tx.set(draftRef,{items:{}})`
把整份草稿清空的同一个提交里永久丢失，且没有任何报错。这比第一个漏洞更隐蔽，
因为它完全发生在"合法的原子事务"内部，表面看流程全对。

修法：写入的内容必须从这次事务里刚读到的 `draftItems` 转换而来，不能用外部传入
的快照。

```js
function buildOrderItemsFromDraft(draftItems){
  const activeIds = Object.keys(draftItems).filter(id => draftItems[id] && draftItems[id].qty > 0);
  const orderedIds = MENU.map(d => d.id).filter(id => activeIds.includes(id));
  const out = [];
  orderedIds.forEach(id => {
    const d = MENU_BY_ID[id];
    if(!d) return;   // 菜单里已经找不到这道菜了（比如被下架），跳过，不让事务因此崩掉
    const it = draftItems[id];
    const entry = { name: dishZhName(d, it), qty: it.qty, price: dishUnitPrice(d, it) };
    if(d.spicy) entry.spice = it.spice;
    if(d.sizes) entry.size = it.size || defaultSizeKey(d);
    if(d.category === 'dumplings') entry.cookMethod = it.cookMethod || 'steamed';
    const excludeKeys = Object.keys(it.excludes || {}).filter(k => it.excludes[k]);
    if(excludeKeys.length) entry.excludes = excludeKeys;
    out.push(entry);
  });
  return out;
}

async function attemptSubmitOrder(order, idempotencyKey){
  const orderRef = ordersRef.doc(idempotencyKey);
  const draftRef = tableCartsRef.doc(order.table);
  let outcome = null;
  await db.runTransaction(async tx => {
    const orderSnap = await tx.get(orderRef);
    if(orderSnap.exists){
      outcome = { status: 'alreadyExists', docId: idempotencyKey };
      return;
    }
    const draftSnap = await tx.get(draftRef);
    const draftItems = (draftSnap.exists && draftSnap.data().items) || {};
    const itemsFromDraft = buildOrderItemsFromDraft(draftItems);
    if(itemsFromDraft.length === 0){
      outcome = { status: 'claimedByOther' };
      return;
    }
    tx.set(orderRef, {
      table: order.table, items: itemsFromDraft, createdAt: order.createdAt,
      nickname: order.nickname, partySize: order.partySize, status: 'pending',
      isAddOn: order.isAddOn,
    });
    tx.set(draftRef, { items: {}, updatedAt: Date.now() });
    outcome = { status: 'created', docId: idempotencyKey };
  });
  return outcome;
}
```

一个 Firestore 事务里原子判定两件事：

1. **`orderRef`（按幂等键定位的订单文档）是否已经存在** → 存在就是本机自己的重试，
   直接复用，不管这次点击距离上一次隔了多久
2. **草稿转换出来的 items 是不是空的** → 空说明同桌另一台设备已经抢先提交并清空过

Firestore 事务是乐观并发控制：如果两次并发的事务读了同一份草稿，先提交的那次成功，
后提交的那次在 commit 时会发现读过的数据已经被改过，SDK 自动重跑整个事务——重跑时
再读一次草稿、也用这次重跑读到的内容重新生成 items，两者现在永远同步，不会再出现
"判断用新数据、写入用旧数据"的缺口。这一步不依赖时间窗口或者内容比较，是数据库
级别的原子判定。

## `claimedByOther` 分支：内容比对退回兜底

```js
const freshOrders = await fetchTableOrders(state.table);
const borrowed = findRecentDuplicateOrder(freshOrders, items, 60000);
if(borrowed){
  docId = borrowed.id;
}else{
  const docRef = await withTimeout(ordersRef.doc(idempotencyKey).set({...}), 12000);
  docId = idempotencyKey;
}
```

幂等键在这个分支帮不上忙——两台设备各自生成的键本来就是互不相关的随机值，没法靠
比较键来判断"这是不是同一份意图"。只能退回内容比对：查最近 **60 秒**内有没有一笔
"菜品/数量/辣度/规格"完全一样的订单，找到就直接复用；这个窗口选得比之前（3 秒/15
秒）宽松，因为现在这是唯一剩下的内容比对场景，不用再分层——足够宽松以接住真实的
同桌协作场景，但依然有上限，不会跟顾客一小时后真的想再点一份一样的菜搞混。

如果连这个也没查到（极小概率——比如对方那笔还没同步到本机能查到的那次读取里），
兜底直接用本机幂等键把订单落地，保证不会卡在"两边都以为对方会交"的僵局里。

## 精确划账：`reconcileDishQtyPairs`（本机购物车 + 共享草稿共用）

`pendingSubmitAttempts`/`sessionStorage` 里记的东西最终都会转成同一种格式——
`dishQtyPairs`：`[{id, qty}]`，只留划账用得到的两个字段。转换函数：

```js
function toDishQtyPairs(dishIds, items){
  return dishIds.map((id, idx) => ({ id, qty: items[idx].qty }));
}
```

拿到 `dishQtyPairs` 之后，`reconcileDishQtyPairs(table, dishQtyPairs)` 做两件事：

1. **本地购物车**：直接按数量扣减内存里的 `state.items`（不是清零），立刻生效。
2. **共享草稿**：在一个 Firestore 事务里现读现减——读到当前草稿的实际内容，只把
   `dishQtyPairs` 里涉及的那几道菜的数量精确减掉，其余菜品（不管是本机后来又加的，
   还是同桌别人加的）原样保留，最后整份 `tx.set(draftRef, {items: draftItems})`
   写回去（这次的"整份写"是用现读到的最新内容重新拼出来的，不是拍脑袋清空）。

`reconcilePendingSubmits`（被动，靠实时监听追上来）和下面的 `reconcileStaleKeyIfResolved`
（主动，下单前先查一次服务器）都调用这一份逻辑，不再各写一遍：

```js
function reconcilePendingSubmits(){
  if(!state.pendingSubmitAttempts.length || !liveTableOrders.length) return;
  const resolved = [];
  state.pendingSubmitAttempts = state.pendingSubmitAttempts.filter(attempt => {
    const matched = liveTableOrders.find(o => o.id === attempt.idempotencyKey);
    if(!matched) return true;
    resolved.push(attempt);
    return false;
  });
  resolved.forEach(attempt => reconcileDishQtyPairs(state.table, toDishQtyPairs(attempt.dishIds, attempt.items)));
}
```

用幂等键（文档 id）做匹配，比之前"createdAt + 菜品内容签名"两个字段一起比对更直接
——同一个 id 只可能对应同一笔提交，不存在巧合撞上的可能。

## 下单前主动核对：`reconcileStaleKeyIfResolved`

**这是修复①（指纹绑定）和修复②（事务内现读现算）各自内部都对、但组合在一起
留下的一个新缺口**，也是外部审阅发现的：

修复①判断"要不要发新键"，依据的是**本机保存的旧指纹**跟这次要提交的内容是否一致
——指纹不一致就发新键，这个判断本身没错。但指纹不一致不等于旧键已经作废：旧键
背后那次提交完全可能已经在服务器上成功建单了，只是本机因为网络问题没收到确认
（`submitOrder()` 走进 `catch`，按设计不清购物车、不清幂等键）。如果这时候本机
购物车里因为某种原因（比如碰了一下已经提交过的那道菜、或者共享草稿的"整份清空"
信号还没被本地监听追上）又混回了已经成交过的内容，修复②又会精确地把"这次事务
读到的草稿"如实写成新订单——于是同一份内容顶着新键，在旧订单之外又落地了一遍，
变成真的重复下单。两个修复各自按设计执行，全程不会报任何错。

这个窗口比原来那两个漏洞更窄——需要叠加"服务器成功但客户端判定失败/超时"这个
前提——但这个前提正是这套系统存在的理由（网络差的餐厅场景），不能当成可以忽略
的边缘情况；而且不能指望靠"等被动的实时监听追上来"兜底，因为监听推送和这次
点击提交走的是同一条网络，网络差的时候两者可能一样慢、甚至监听更慢，用户完全
可能在监听追上之前就已经点了第二次确认。

修法：在**生成新键之前**，主动查一次服务器（不吃本地监听缓存），确认旧键是不是
已经真实落地了：

```js
async function reconcileStaleKeyIfResolved(table){
  const storageKey = IDEMPOTENCY_KEY_PREFIX + table;
  let cached = null;
  try{ cached = JSON.parse(sessionStorage.getItem(storageKey) || 'null'); }catch(e){}
  if(!cached) cached = memoryIdempotencyKeys[table] || null;
  if(!cached || !cached.key) return;

  let exists = false;
  try{
    const oldOrderSnap = await withTimeout(ordersRef.doc(cached.key).get({ source: 'server' }), 5000);
    exists = oldOrderSnap.exists;
  }catch(e){ return; }
  if(!exists) return;

  const attempt = state.pendingSubmitAttempts.find(a => a.idempotencyKey === cached.key);
  const dishQtyPairs = attempt ? toDishQtyPairs(attempt.dishIds, attempt.items) : (cached.items || []);
  if(attempt){
    state.pendingSubmitAttempts = state.pendingSubmitAttempts.filter(a => a !== attempt);
  }
  await reconcileDishQtyPairs(table, dishQtyPairs);
  clearIdempotencyKey(table);
}
```

`submitOrder()` 一开始（在读购物车、算 `items`、决定用哪个幂等键之前）就先 `await`
这个函数。如果旧键确认已经落地，就先把对应的菜从本地购物车和共享草稿里都精确
划掉、旧键作废，剩下的才是这次真正要提交的新内容；如果核对完购物车因此被划空了
（这次要交的东西其实早就交过了），直接当无事发生，不用再提交一次。

查不到 / 这次额外的查询本身超时失败，就什么都不做，照旧走后面的指纹比对逻辑——
这一步只是多一层保险，不能因为它自己失败就把整个下单流程卡住，也不会改变任何
既有场景（全新提交时 `cached` 为空，直接跳过，不产生额外的网络往返）。

**找不到 `attempt`（比如中途刷新过页面，`state.pendingSubmitAttempts` 这个内存
数组被重置了）不会让精确划账失效**：`getOrCreateIdempotencyKey` 存键的时候，会把
`dishQtyPairs` 跟 `{key, fingerprint}` 一起存进 `sessionStorage`（活得过页面刷新），
找不到内存里的 `attempt` 就退化用 `cached.items` 兜底，两条路径最终走的是同一份
`reconcileDishQtyPairs`，划账结果一致。

## 这一步为什么不能整份覆盖共享草稿（`clearSharedCart` 已删除）

**这里也有一个已确认修复的漏洞**：`reconcileStaleKeyIfResolved` 和
`reconcilePendingSubmits` 最初的版本，在确认旧键已经落地之后，都会调用一个
`clearSharedCart()`——对共享草稿文档做一次 `.set({items:{}})` 整份覆盖清空，理由是
"万一当时清空草稿的那次请求本身也超时了"。这个理由站不住脚：`attemptSubmitOrder`
的事务里，建单（`tx.set(orderRef,...)`）和清空草稿（`tx.set(draftRef,{items:{}})`）
是**同一个 Firestore 事务**，要么一起提交要么一起不提交，不存在"订单建成了但草稿
没跟着清空"这种独立失败的情况；唯一不走这个事务的兜底分支（`claimedByOther` 时
如果 60 秒内没查到匹配订单，直接 `.set()` 建单）也是建立在"进入这条分支之前，
草稿已经确认为空"的前提上。也就是说：**只要能确认某个幂等键对应的订单存在，草稿
在那时候就已经被正确处理过了**，事后再补一次整份清空，不会修复任何东西，只会
冒着把同桌其他设备这段时间新加的合法内容一起静默抹掉的风险——跟前两个漏洞是
同一类症状（内容被覆盖式清空，而不是按需精确移除）。

修法：`clearSharedCart()` 这个函数已经从代码里删掉，两处调用都换成了
`reconcileDishQtyPairs` 里那段"事务内现读、只精确扣掉涉及的那几道菜、其余原样
保留"的写法（见上一节）。`submitOrder()` 成功之后清购物车、以及"继续点单"按钮
（`resetToMenu()`）里，原来各自也有一次同样逻辑的整份清空调用，一并改掉了。

## 完整流程图

```
submitOrder()
  ├─ reconcileStaleKeyIfResolved(table)                    // 主动查一次旧键是否已落地
  │    └─ 已落地 → 精确划掉本地购物车/共享草稿里对应的菜、旧键作废
  ├─ 购物车因此被划空 → 当无事发生，不再提交
  ├─ 本地算出 items（购物车里数量>0的菜）
  ├─ idempotencyKey = getOrCreateIdempotencyKey(table, items, itemDishIds)   // 指纹一致才复用，否则发新键
  ├─ 记一条 pendingSubmitAttempts（万一后面失败，留给事后核对）
  ├─ fetchTableOrders(table)                              // 用于 isAddOn 判断 + 兜底汇总
  ├─ attemptSubmitOrder(order, idempotencyKey)             // 合并事务
  │    ├─ orderRef 已存在 → alreadyExists（本机重试）
  │    ├─ 草稿已空 → claimedByOther（被同桌抢了）
  │    │    ├─ 查最近 60 秒内容匹配的订单 → 找到就复用
  │    │    └─ 没找到 → 兜底直接用幂等键建单
  │    └─ 都不是 → created（正常建单 + 清空草稿）
  ├─ [任何异常/超时] → alert 失败，不清购物车/幂等键，留给 reconcilePendingSubmits
  └─ [拿到 docId] → 清幂等键、翻到成功页（不等后续汇总请求，也不再整份覆盖共享草稿）
       └─ 后台补一次更准的汇总，失败不影响已经成功的下单
```

## 已修复的四个漏洞（都是外部审阅发现的，均已修复并验证过语法）

前两个的共同点是同一类症状：顾客明明加了菜，最终却没出现在任何订单里，系统全程
显示"成功"——比重复下单更难发现，因为重复下单至少能从多出来的一张单子上看出
问题，丢单是安静的，只有账对不上时才会被发现。后两个反过来，是前面的修复组合后
才出现的新缺口，症状是重复下单和内容被静默覆盖。四者触发路径完全不同，必须分别
修，修一个不能替代另一个：

1. **键只绑定桌号，不绑定内容**（发生在 `alreadyExists` 分支）——见上面"幂等键"
   一节。同一台设备先后两次提交、内容变了，会被误判成同一次重试。已修复：键改成
   绑定内容指纹，指纹不一致就发新键。
2. **事务判断用的草稿数据和写入订单的数据是两份**（发生在 `created` 主路径）——见
   上面"合并事务"一节。跨设备并发编辑同一份草稿时，Firestore 的自动重试机制会
   用最新数据通过存在性判断，但写入仍用旧快照，新增的菜连同整份草稿一起被清空。
   已修复：写入内容改成从事务里刚读到的草稿现算。
3. **修复①和修复②组合后的交叉缺口**——指纹不匹配就发新键（修复①）+ 写入内容永远
   如实反映当前草稿（修复②），两者叠加在"旧键其实已经成功、但本机购物车又混回
   了已成交内容"这个窗口里会导致重复下单。已修复：见上面"下单前主动核对"一节，
   生成新键前先同步查一次服务器，不依赖被动监听追上来。
4. **确认旧键落地后，用整份覆盖清空共享草稿**——见上面"为什么不能整份覆盖共享
   草稿"一节。会把同桌其他设备同一时间新加的合法内容一起静默抹掉。已修复：改成
   事务内现读现减，只精确扣掉这次核对涉及的那几道菜。

## 仍然存在的设计取舍（审阅时请重点看这几条）

1. **`claimedByOther` 分支仍然依赖内容比对 + 60 秒窗口**，不是完全消除了"猜"的成分
   ——这是因为跨设备场景没有共享的标识符可用，理论上还是存在"60 秒内两笔独立的
   同内容订单被误合并"的极小概率。
2. **sessionStorage 不可用时退化成纯内存变量**，会失去"扛得住页面刷新"这个特性，
   但不会导致功能崩溃（退化到接近本机重试完全没有保护的状态，等同于直接进
   `claimedByOther` 式的内容比对兜底）。
3. **两台设备内容不同、近乎同时提交**：设计上会各自成功创建各自的订单（因为
   `claimedByOther` 分支的兜底逻辑最终会用提交方各自的 `items` 落地）——这被认为是
   正确行为，不是漏洞：不能因为"内容不同"就误判成需要合并或拦截。
4. **`reconcileStaleKeyIfResolved` 自己也可能超时/失败**（查询本身走的也是同一条
   可能很差的网络）——查不到就退回原来的指纹比对逻辑，不会让下单流程卡死，但也
   意味着这层保险不是 100% 保证生效，只是把原来完全依赖被动监听的窗口大幅收窄。
5. **`sessionStorage` 仍然是"一张桌子一个当前幂等键"的单槽位设计，不是待处理键
   的数组**：如果指纹不匹配要发新键的那一刻，`reconcileStaleKeyIfResolved` 对旧键
   的查询恰好失败/超时，旧键会被新键直接覆盖掉；只要没有紧接着刷新页面，内存里
   的 `pendingSubmitAttempts` 还留着这条记录，被动的 `reconcilePendingSubmits` 仍
   有机会追上来核对；但如果这之后又恰好刷新了页面，这个旧键就再也没有人会去查了
   ——**这是权衡后有意留下的**：要彻底堵上，需要把单槽位改成待处理键数组、加上
   过期清理，是一次更大的结构改动，而触发条件是"指纹不匹配的重试"+"核对查询失败"
   +"紧接着刷新页面"三者同时发生，比第 4 条修复之前的窗口窄得多。如果这一条本身
   也需要收紧，可以再单独安排一版，不和这次的改动混在一起。
6. **12 秒客户端超时、没有离线持久化、没有逐菜品"已发送"可见状态**——这几项还没做，
   是下一步的候选，跟这次的幂等键改动是分开的层面。
